# 代码画布 v0.1.4 · 应用内更新 + 外部评审修复

这一版做两件事：**让更新不再需要去仓库拉**，以及**把外部评审挑出来的真问题修掉**。

上一版（v0.1.3）我只保证了「数值达标、测试全绿、不崩溃」，并且把一次只看了首页与预览页的自审当成了验收通过——夜间代码页正文几乎不可读，我却说「夜间非常优秀」。这一版的口径改了：**以模拟器实拍画面逐屏自审为准**，并且把整个工程源码与实拍图交给外部模型做全维度评审（逻辑、页面、功能、美观、交互、实际体验、更新方案），评审结论逐条核实后再改。

---

## 一、应用内自动更新（本版重点）

以前更新只能靠 GitHub 仓库页/Release 资产——大陆网络下这条链路本身就不通，等于没有更新。现在：

| 环节 | 做法 |
|---|---|
| 版本清单来源 | 自建源优先 `relay.zhuquan.xyz/dl/codecanvas-latest.json`（Cloudflare 前缀，国内可直连），其次 GitHub raw，最后 GitHub API；每个源失败会记下原因并换下一个 |
| 安装包地址 | 清单里的 `apkUrl` 指向自建源的**带版本号文件**，并附内容寻址参数（`?v=<清单摘要前 12 位>`）——文件内容一变 URL 就变，CDN 不可能再用旧包；`fallbackApkUrl` 指向 GitHub Release 资产，主地址失败自动换地址重下 |
| 防盗链/防投毒 | 地址白名单（只接受本域名 `/dl/*.apk` 与 GitHub 资产域）、清单 schema/版本号/摘要/大小校验、下载字节上限、SHA-256 校验、包名+versionCode 必须与清单一致、**签名必须与已安装版本相同** |
| 交互 | 首页「我的文件」标题行上的 `检查更新`（有新版才变主色），长按进设置可关掉自动检查；下载有进度，取消会真的中断连接 |
| 失败可读 | 取清单失败会把「哪个源、什么错」列出来；下载校验失败会**分清是大小不符还是摘要不符并给出两侧数值**（原来只有一句「校验失败」）；被系统拦住安装会明确说是 Android 的安装权限门 |

**实测（模拟器，真实网络，非预览）**：

- 清单与安装包在公网自建源上实测可取（`http=200`，下载 83,487 字节，SHA-256 与清单一致）。
- 装一个 versionCode=4 的构建（源码与本版一致），启动后应用内直接显示 `新版本 0.1.4 · 更新` → 点开确认框 → 从自建源下载 → SHA-256/包名/版本/签名逐项通过 → 交给系统安装器（截图见 `docs/evidence/v0.1.4/update_offer.png`、`update_after_download.png`、`update_installer_handoff.png`）。
- **安装真的落地了**：在系统安装器里确认后，模拟器上的应用由 **versionCode 4 变成 5 / 0.1.4**，系统安装器自报 `App updated`；重开应用点「检查更新」，显示 `已是最新 · 0.1.4`（截图 `update_applied_latest.png`）。这是应用内更新从自建源一路走到安装完成的完整证据。
- **这一跳在测试模拟器上是怎么做的**：模拟器装了 Google Play Protect，对「它没见过的自签名包」会弹「Harmony app blocked / 扫描」且不提供「仍然安装」。这是**系统级安全门**，应用侧不该也不能绕过。为了把链路验证完，我在**这台一次性测试模拟器**上临时关闭了 Play Protect、装完立即恢复（`package_verifier_enable` 已还原为 1，Play 商店已重新启用，安装未知来源权限也还原为默认）。
- **对你真机的含义**：真机首次安装这类自签名包时，系统会弹一次确认（允许安装未知来源 / Play Protect 提示），点过之后才能装；这是 Android 的设计，不是更新器的问题。我**没有**在你的手机上改任何安全设置。

## 二、外部评审挑出的问题（已修）

| # | 问题（评审指出，我核实后确认） | 根因 | 修法 |
|---|---|---|---|
| 1 | **夜间代码页正文几乎不可读**（P0） | 夜间 `canvas_code_ink` 是近黑色 `#0F172A`，而代码区实际底色是 `#101722`；更糟的是对比度测试比的是**已经没人用的死资源** code_bg_light（夜间仍为浅色），所以测试永远是绿的 | 夜间正文改 `#DDE7F5`；删掉死资源；断言改比真实底色 `canvas_code_surface`；新增**真实控件**对比度仪器测试 |
| 2 | 长 SVG / 大文档被当成纯文本显示 | 渲染类型只看前 3000 字符里有没有 `</svg>`，长文档的结束标签在窗口之外 | 改成解析**根元素**：`<!doctype html>`/`<html>`/`<svg>` 优先，其次看扩展名与根标签，不再依赖固定长度前缀 |
| 3 | 读文件失败会静默新建**空文档**，看起来像「文件被清空了」 | 打开失败与「新文档」共用一条路径，空流还会被存成空文档 | 读失败则禁用编辑与保存并明确报错；空流拒绝导入 |
| 4 | 「已保存」会撒谎 | 保存是 fire-and-forget，旧的写盘可能覆盖新的，且没有任何版本概念 | 文档加 `revision` 单调递增，写入前校验；`DocumentSaveCoordinator` 单飞，旧 revision 的写入被拒 |
| 5 | 分享/导出的文件名会把 `#`、`%` 原样塞进 URI，部分接收方打不开 | 文件名净化没有处理 URI 保留字符 | 新增 `ShareExporter`：转义保留字符、保证唯一文件名、收窄 MIME |
| 6 | XML 预览的「格式化」会改写正文语义 | 按 `<`/`>` 硬切分并重排，属性里带 `>`、CDATA、混合内容都会被改义 | 只在**结构安全**时才格式化（元素嵌套、无文本内容），否则原样展示；并加深度与长度上限 |
| 7 | 预览渲染进程崩溃/被回收会把整个应用一起带走 | 没有实现 `onRenderProcessGone`，且每次加载都换一个新的 WebViewClient | 一个客户端管到底；崩溃/回收时拆掉死的 WebView、明确告知、可一键重建预览；其余 WebView 调用都做了空保护 |
| 8 | **空白缩略图会把文件类型封面盖成白框**（我自己逐屏看图时发现，评审没提到） | 缩略图先铺白底再抓帧，页面没画完就抓会存下一张纯白图 | 抓到的帧若近似单色即判定「什么都没画」，不存；读到时也丢弃并回退类型封面（新增仪器测试） |
| 9 | 主页底部固定一条「检查更新」，把页面拉成「内容 + 大空档 + 页脚」 | 更新入口被放在根布局最后 | 挪到「我的文件」标题行，底部不再有页脚 |
| 10 | 方格卡片固定 152dp，时间「10-01 15:18」被卡片底边裁掉 | 固定高度 + 四个字段抢同一块高度，大字体只会更严重 | 改 `wrap_content` + `minHeight`，实测三种卡片时间行完整 |
| 11 | 编辑器上部工具栏层级过高，代码区被挤到很低 | 标题栏 58dp、分段 48dp、动作行 48dp 三层叠着 | 52dp / 44dp / 44dp，按钮保持 40dp 不裁切 |
| 12 | 撤销栈无内存上限（50 份全文快照，大文档能吃掉上百 MB） | 只按条数限制，不看文本量 | 加总字符预算，超了从最旧的快照开始丢 |
| 13 | 导出/分享文案分不清导的是什么 | 文案是「导出」「分享」 | 改「导出源码文件」「分享源码」 |

## 四、**没做到**的部分（诚实清单）

评审给的清单比这一版能塞进去的长。以下是我**明确知道、但这一版没有做**的，留在这里而不是悄悄略过：

1. **代码编辑器仍然没有行号栏**——上一版就欠着，这一版仍然没有。
2. **未在小米 Turbo 3 真机测试**。所有实拍都来自模拟器（1080×2400）；真机字体（MiSans）、厂商省电策略、安装器的具体措辞都可能不同。
3. 评审的这几条 P1/P2 视觉与页面项本版未改（都是「改了会更好、不改也不算坏」）：
   - 列表模式与方格模式的浏览密度差异不够明确（列表仍偏卡片）；
   - 窄屏/大字体下的元信息优先级（时间挤压、标题过早省略）；
   - 预览页的「联网加载」「脚本」开关应收进一个预览设置菜单；
   - 夜间预览的黑色画布与应用深蓝背景之间有断层；
   - 图标语义与风格统一（如「更多」的语义）；
   - 内置示例内容的比例不足以验证真实渲染能力。
4. 更新方案评审建议的**内置证书指纹**（把正式签名 SHA-256 编译进应用，而不只是比对待安装包与已安装包的签名）本版未做；当前强度是「必须与已安装应用同签名 + 清单摘要 + 白名单地址」。
5. 老版本（≤0.1.3）**不会**通过自建源收到这一版——它们的更新器只认 GitHub。这一版是手动装一次之后，后续版本才能走应用内更新。
6. 评审提到的**文本长度上限不统一**（粘贴按 2M 字符、存储按 50MB 字节，且编辑框没有输入过滤器阻挡超限输入）本版未改。直接给编辑框加逐次输入过滤器会在大文本上每敲一个字做一次全量 UTF-8 长度计算，需要先设计成低成本判断再上，否则是拿卡顿换一个本来就不常见的场景。
7. 评审提到的**主页搜索过滤在主线程**本版未改（改动涉及适配器过滤流程，属于「长时间卡顿」风险项而非当前可见缺陷）。

下一版（0.1.5）建议顺序：行号栏 → 真机验证 → 列表/方格密度 → 预览设置菜单 → 内置证书指纹。
